# الدرس الثاني: كيف يعمل المعالج من الداخل؟

## مصطلحات مهم تعرفها قبل ما نبدأ

| المصطلح | المعنى |
|---------|--------|
| Program Counter — PC | سجل يحتوي عنوان التعليمة التالية |
| Instruction Register — IR | سجل يحتوي التعليمة قيد التنفيذ حالياً |
| Register | وحدة تخزين صغيرة جداً داخل المعالج مباشرة |
| Clock Speed | سرعة المعالج بالـ GHz |
| IPC — Instructions Per Cycle | عدد التعليمات المنفذة في كل دورة |
| Pipelining | تقنية معالجة عدة تعليمات في آن واحد |
| Branch Prediction | تنبؤ المعالج بمسار الكود قبل تنفيذه |
| Context Switching | تبديل المعالج بين عدة Processes بالتناوب |
| ISA — Instruction Set Architecture | مجموعة التعليمات التي يفهمها المعالج |
| x86-64 | معمارية Intel و AMD المستخدمة في السيرفرات التقليدية |
| ARM | معمارية المعالجات الأكثر كفاءة طاقوياً |

---

## شرح المفاهيم

### أولاً: الـ Registers

الـ Register هو أصغر وأسرع وحدة تخزين في الحاسوب، موجودة داخل المعالج مباشرة. لا تحتاج أسلاكاً خارجية للوصول إليها مما يجعلها أسرع من الـ Cache نفسه.

```
أنواع الـ Registers الأساسية:

Program Counter (PC)    ← عنوان التعليمة التالية
Instruction Register(IR)← التعليمة قيد التنفيذ الآن
General Purpose (R1,R2) ← تخزين بيانات مؤقتة
Stack Pointer (SP)      ← يتتبع أعلى الـ Stack
Flags Register          ← نتائج المقارنات
```

### ثانياً: دورة الـ CPU بالتفصيل

```
FETCH:
المعالج يذهب للعنوان الموجود في PC
يجلب التعليمة ويضعها في IR
PC يزيد تلقائياً للعنوان التالي
         ↓
DECODE:
المعالج يقرأ IR ويحلل التعليمة:
- ما نوع العملية؟
- ما المدخلات؟
- أين تُخزن النتيجة؟
         ↓
EXECUTE:
المعالج ينفذ العملية فعلياً
النتيجة تُخزن في Register أو RAM
```

ملاحظة جوهرية: الـ PC يزيد فور انتهاء مرحلة FETCH وليس بعد انتهاء الدورة كاملة. هذا ضروري لتمكين الـ Pipelining.

### ثالثاً: مثال كامل

```php
$a = 5;
$b = 3;
$c = $a + $b;
```

تتحول هذه التعليمات إلى:

```
العنوان  التعليمة
1040     LOAD 5  → R1
1041     LOAD 3  → R2
1042     ADD R1 + R2 → R3
1043     STORE R3 → Memory[$c]
```

تنفذ الدورة أربع مرات متتالية حتى تكتمل العملية.

### رابعاً: Clock Speed والأداء الحقيقي

سرعة المعالج وحدها لا تكفي لتقييم أدائه. الأداء الفعلي يعتمد على:

```
الأداء = Clock Speed × IPC × عدد Cores

مثال:
CPU الأول:  2 GHz × 2 IPC = 4 مليار تعليمة/ثانية
CPU الثاني: 3 GHz × 1 IPC = 3 مليار تعليمة/ثانية

الأول أسرع رغم أن GHz أقل.
```

### خامساً: Pipelining

تقنية تسمح للمعالج بمعالجة عدة تعليمات في وقت واحد بأن يبدأ FETCH للتعليمة التالية بينما يُنفذ EXECUTE للتعليمة الحالية.

```
بدون Pipelining:
[FETCH 1][DECODE 1][EXECUTE 1]
                               [FETCH 2][DECODE 2][EXECUTE 2]

مع Pipelining:
[FETCH 1][DECODE 1][EXECUTE 1]
         [FETCH 2][DECODE 2][EXECUTE 2]
                  [FETCH 3][DECODE 3][EXECUTE 3]
```

**Branch Prediction:** عندما يواجه المعالج شرطاً مثل if، يتنبأ بالفرع الذي سيُنفذ ويبدأ جلبه مسبقاً. إذا أخطأ التنبؤ يجب مسح الـ Pipeline وإعادة البدء من الفرع الصحيح مما يُضيع 10-20 دورة.

### سادساً: Context Switching

المعالج يُعطي كل Process شريحة زمنية قصيرة ثم ينتقل للتالية. عند كل انتقال يحفظ حالة الـ Registers الحالية ثم يُحمل حالة الـ Process التالية. هذا يستغرق وقتاً يُسمى Context Switching Overhead.

في سياق Laravel: إذا زاد عدد PHP Workers بشكل كبير عن عدد الـ Cores يزداد Context Switching ويرتفع استهلاك المعالج دون زيادة حقيقية في الأداء.

### سابعاً: معماريات المعالجات

```
x86-64:
تصنعها Intel و AMD
تُستخدم في معظم السيرفرات التقليدية
تعليمات كثيرة ومعقدة — CISC

ARM:
تُستخدم في الهواتف و Apple M-series و AWS Graviton
تعليمات أقل وأبسط — RISC
استهلاك طاقة أقل وكفاءة أعلى في بعض الأحمال
```

عند نشر التطبيق على AWS يمكن الاختيار بين سيرفرات x86 التقليدية وسيرفرات Graviton المبنية على ARM والأرخص في بعض الحالات.

## الأسئلة والإجابات

**السؤال الأول:** ما هو الـ Program Counter وما الذي يحدث له بعد كل Fetch؟

الـ Program Counter سجل داخل المعالج يحتوي عنوان التعليمة التالية التي يجب تنفيذها. يزيد تلقائياً فور انتهاء مرحلة Fetch وليس بعد انتهاء الدورة كاملة، وذلك لتمكين الـ Pipelining من بدء جلب التعليمة التالية بينما تُنفذ الحالية.

---

**السؤال الثاني:** ما الفرق بين الـ Register والـ RAM؟

الـ Register موجود داخل المعالج مباشرة ويُصنف كأسرع وحدة تخزين في الحاسوب بزمن وصول أقل من 0.3 نانوثانية، لكنه صغير جداً إذ لا يتجاوز بضع bytes. أما الـ RAM فتوجد خارج المعالج على اللوحة الأم بزمن وصول يصل إلى 100 نانوثانية، لكنها أكبر بكثير إذ تتراوح بين 8 و 64 GB في الأنظمة الحديثة.

---

**السؤال الثالث:** لماذا لا يكفي عدد الـ GHz وحده لتقييم سرعة المعالج؟

لأن الأداء الفعلي يعتمد على ثلاثة عوامل مجتمعة: سرعة الساعة بالـ GHz، وعدد التعليمات المنفذة في كل دورة IPC، وعدد الـ Cores. معالج بـ 2 GHz وIPC يساوي 2 ينفذ 4 مليار تعليمة في الثانية، وهو أسرع من معالج بـ 3 GHz وIPC يساوي 1 ينفذ 3 مليار تعليمة فقط.

---

**السؤال الرابع:** ما هو الـ Pipelining وكيف يزيد الأداء؟

الـ Pipelining تقنية تسمح للمعالج بمعالجة عدة تعليمات في آن واحد. بينما يُنفذ EXECUTE للتعليمة الأولى، يُحلل DECODE التعليمة الثانية، ويجلب FETCH التعليمة الثالثة. هذا يزيد الإنتاجية دون رفع سرعة الساعة.

---

**السؤال الخامس:** ما هو Branch Prediction وما العلاقة بينه وبين الـ Pipelining؟

عندما يواجه المعالج شرطاً في الكود مثل if، فإن الـ Pipelining تجعله يجلب التعليمات التالية مسبقاً قبل معرفة نتيجة الشرط. الـ Branch Prediction خوارزمية داخل المعالج تتنبأ بالفرع الذي سيُنفذ. إذا أخطأ التنبؤ وجب مسح ما جُلب وإعادة البدء من الفرع الصحيح مما يُضيع دورات معالجة.

---

**السؤال السادس:** ما هو الـ Context Switching وما تكلفته؟

Context Switching انتقال المعالج من Process إلى أخرى مع حفظ حالة الأولى واستعادة حالة الثانية. يتضمن حفظ كل الـ Registers وتحميل Registers الـ Process التالية. له تكلفة زمنية حقيقية، وإذا زاد عدد الـ Processes بشكل كبير قضى المعالج وقتاً أطول في إدارة التبديل من في التنفيذ الفعلي.

---

**السؤال السابع:** في سياق تطبيق Backend يخدم آلاف المستخدمين، كيف يؤثر عدد الـ Cores؟

كل Request في Laravel يحتاج Worker Process. مع 4 Cores تُعالج 4 Requests في وقت واحد فعلياً والباقي ينتظر في Queue. مع 8 Cores تُعالج 8 Requests في وقت واحد مما يقلل وقت الانتظار ويرفع عدد الطلبات التي يستطيع السيرفر معالجتها في الثانية.

---

**السؤال الثامن:** في PHP، كل Request يُنشئ Process جديدة. كيف تختلف Node.js في هذه النقطة؟

PHP التقليدي يُنشئ Process منفصلة لكل Request، وكل Process تستهلك RAM مستقلة. 1000 مستخدم تعني 1000 Process. أما Node.js فتستخدم Process واحدة مع Event Loop يُدير كل الـ Requests. هذا يوفر RAM لكنه يخلق مشكلة: عملية ثقيلة حسابياً تُوقف Event Loop وتُعطل جميع المستخدمين في آن واحد.

---

## ملاحظات الأداء

- ضبط عدد PHP-FPM Workers بما يتناسب مع عدد الـ CPU Cores يمنع الـ Context Switching المفرط.
- تطبيقات Web تقضي معظم وقتها في انتظار Database و Network وليس في عمليات حسابية، لذلك زيادة الـ Cores أنفع من رفع سرعة الساعة في هذا السياق.
- سيرفرات AWS Graviton المبنية على ARM قد تكون أوفر تكلفة لبعض أنواع التطبيقات.

---

## ملخص

المعالج يعمل بدورة ثلاثية متكررة: Fetch ثم Decode ثم Execute. الـ Program Counter يتتبع موضع التنفيذ ويتقدم فور انتهاء الـ Fetch. الـ Registers توفر أسرع تخزين ممكن داخل المعالج نفسه. الـ Pipelining ترفع الكفاءة بمعالجة عدة تعليمات في آن واحد لكنها تخلق تحدي الـ Branch Prediction. الأداء الحقيقي للمعالج ليس رقم الـ GHz وحده بل محصلة Clock Speed وIPC وعدد Cores. فهم هذه المفاهيم يمكّن مهندس الـ Backend من اتخاذ قرارات صحيحة في اختيار السيرفر وضبط إعداداته.
