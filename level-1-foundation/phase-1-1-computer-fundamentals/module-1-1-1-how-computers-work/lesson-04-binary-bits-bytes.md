# الدرس الرابع: البيانات الثنائية — كيف يخزن الحاسوب كل شيء؟

## مصطلحات مهم تعرفها قبل ما نبدأ

| المصطلح | المعنى |
|---------|--------|
| Bit | أصغر وحدة بيانات، قيمتها 0 أو 1 |
| Byte | 8 Bits مجتمعة |
| Binary — Base 2 | نظام العد الثنائي يستخدم 0 و 1 فقط |
| Decimal — Base 10 | نظام العد العشري المألوف للبشر |
| Hexadecimal — Base 16 | نظام العد السداسي عشر يستخدم 0-9 و A-F |
| Signed Integer | عدد صحيح يمكن أن يكون سالباً |
| Unsigned Integer | عدد صحيح موجب فقط |
| Two's Complement | طريقة تمثيل الأعداد السالبة في Binary |
| Float — IEEE 754 | معيار تخزين الأعداد العشرية |
| Floating Point Error | خطأ دقة ناتج عن تمثيل الكسور في Binary |
| ASCII | معيار ترميز 128 رمزاً بـ 7 bits |
| Unicode | معيار عالمي يُعطي كل رمز في كل لغة رقماً فريداً |
| UTF-8 | طريقة تخزين Unicode تستخدم 1 إلى 4 bytes للرمز الواحد |
| utf8mb4 | دعم MySQL الكامل لـ UTF-8 بما يشمل الـ Emojis |
| Magic Bytes | bytes ثابتة في بداية الملف تُعرّف نوعه الحقيقي |
| MIME Type | نوع الملف الحقيقي كما يراه النظام |

## شرح المفاهيم

### أولاً: لماذا Binary؟

السبب ليس اختياراً تصميمياً بل ضرورة فيزيائية. الترانزستور — اللبنة الأساسية للدوائر الإلكترونية — له حالتان فقط: مفتوح أو مغلق، لا تيار أو يمر تيار. استخدام مستويات كهربائية متعددة لتمثيل أرقام 0-9 يجعل النظام عرضة للأخطاء بسبب تذبذب الكهرباء الطبيعي. بحالتين فقط يكون الهامش واسعاً وأمان الكشف مرتفعاً.

```
0.0v إلى 0.4v = 0 بوضوح
0.6v إلى 1.0v = 1 بوضوح
```

### ثانياً: نظام العد الثنائي

```
النظام العشري (Base 10):
325 = 3×10² + 2×10¹ + 5×10⁰
    = 300 + 20 + 5

النظام الثنائي (Base 2):
1101 = 1×2³ + 1×2² + 0×2¹ + 1×2⁰
     = 8 + 4 + 0 + 1
     = 13
```

**التحويل من Decimal إلى Binary بطريقة القسمة المتكررة:**

```
مثال: تحويل 42

42 ÷ 2 = 21  باقي 0
21 ÷ 2 = 10  باقي 1
10 ÷ 2 = 5   باقي 0
5  ÷ 2 = 2   باقي 1
2  ÷ 2 = 1   باقي 0
1  ÷ 2 = 0   باقي 1

القراءة من الأسفل للأعلى: 101010
التحقق: 32+0+8+0+2+0 = 42 
```

### ثالثاً: وحدات البيانات

```
1 Bit      = 0 أو 1
8 Bits     = 1 Byte
1024 Bytes = 1 Kilobyte  (KB)
1024 KB    = 1 Megabyte  (MB)
1024 MB    = 1 Gigabyte  (GB)
1024 GB    = 1 Terabyte  (TB)
```

خطأ شائع: شركات الإنترنت تقيس السرعة بـ Megabits وليس Megabytes.

```
سرعة 100 Mbps = 100 ÷ 8 = 12.5 MB/s فعلياً
```

### رابعاً: تخزين الأرقام

**الأعداد الصحيحة:**

```
INT في MySQL: 32-bit signed
الحد الأقصى: 2,147,483,647

BIGINT في MySQL: 64-bit signed
الحد الأقصى: 9,223,372,036,854,775,807
```

استخدام INT للـ IDs في جداول ستنمو بشكل كبير خطأ شائع. عند تجاوز 2.1 مليار سجل يفشل MySQL في إنشاء ID جديد. الحل: استخدام BIGINT من اليوم الأول.

**الأعداد العشرية:**

الـ Float يعاني من Floating Point Precision Error. 0.1 في Binary سلسلة لا تنتهي مثل 1/3 في العشري.

```php
$a = 0.1 + 0.2;
var_dump($a == 0.3); // false

echo $a; // 0.30000000000000004
```

لا يُستخدم Float لتخزين المبالغ المالية أبداً. الحل: تخزين المبالغ كأعداد صحيحة بالهللات أو السنتات، أو استخدام BCMath.

```php
$result = bcadd('0.1', '0.2', 10); // '0.3000000000'
```

### خامساً: تخزين النصوص

**ASCII:** يُعطي 128 رمزاً أرقاماً من 0 إلى 127. يكفي للحروف الإنجليزية والأرقام والرموز الأساسية. لا يكفي للعربية أو الصينية أو الـ Emojis.

**Unicode:** يُعطي كل رمز في كل لغة رقماً فريداً يُسمى Code Point.

```
A  = U+0041
ب  = U+0628
😊 = U+1F60A
```

**UTF-8:** الطريقة الأكثر شيوعاً لتخزين Unicode.

```
حروف إنجليزية: 1 byte  (متوافق مع ASCII)
حروف عربية:    2 bytes
رموز نادرة:    3-4 bytes
```

```php
strlen("مرحبا")    // 10 ← عدد الـ bytes وليس الحروف
mb_strlen("مرحبا") // 5  ← عدد الحروف الفعلي
```

**utf8mb4 في MySQL:** يجب دائماً استخدام utf8mb4 وليس utf8 في MySQL. utf8 في MySQL يدعم 3 bytes فقط مما يمنع تخزين الـ Emojis التي تحتاج 4 bytes.

### سادساً: Hexadecimal

كل رمز Hex يساوي 4 bits. رمزان يساويان byte واحد.

```
F    = 1111
A    = 1010
FA   = 1111 1010 ← byte واحد
```

يظهر Hexadecimal في:

```
ألوان CSS:  #FF5733
            FF=255, 57=87, 33=51 → RGB(255, 87, 51)

Hash:       md5("hello") = "5d41402abc4b2a76b9719d911017c592"
            كل حرفان = byte واحد = 16 bytes إجمالاً

URL Encoding:
            %20 = مسافة (hex 20 = decimal 32 = space في ASCII)
```

### سابعاً: Magic Bytes وأمان رفع الملفات

كل نوع ملف له bytes ثابتة في بدايته تُعرّفه بغض النظر عن امتداده.

```
JPEG: FF D8 FF
PNG:  89 50 4E 47
PDF:  25 50 44 46
```

```php
// طريقة خاطئة — سهل خداعها
$extension = $file->getClientOriginalExtension();
if ($extension === 'jpg') { ... }

// طريقة صحيحة — تقرأ Magic Bytes الفعلية
$mimeType = $file->getMimeType();
if ($mimeType === 'image/jpeg') { ... }
```

## الأسئلة والإجابات

**السؤال الأول:** حوّل 25 من Decimal إلى Binary.

```
25 ÷ 2 = 12  باقي 1
12 ÷ 2 = 6   باقي 0
6  ÷ 2 = 3   باقي 0
3  ÷ 2 = 1   باقي 1
1  ÷ 2 = 0   باقي 1

النتيجة: 11001
التحقق: 16+8+0+0+1 = 25 
```

---

**السؤال الثاني:** سيرفر Bandwidth = 1 Gbps. كم ملف حجمه 500 MB يمكن نقله في الثانية؟

```
1 Gbps = 1,000,000,000 bit/s
       = 1,000,000,000 ÷ 8
       = 125 MB/s

125 MB/s ÷ 500 MB = 0.25 ملف/ثانية
أي يحتاج الملف الواحد 4 ثوانٍ للنقل.

ملاحظة: هذا الحد النظري الأقصى.
الأداء الفعلي أقل بسبب TCP Overhead وتقاسم الـ Bandwidth.
```

---

**السؤال الثالث:** ما الفرق بين `strlen()` و `mb_strlen()` في PHP؟

`strlen()` تحسب عدد الـ bytes وليس عدد الحروف. `mb_strlen()` تحسب عدد الحروف الفعلي مع دعم Multi-byte Characters. مع النصوص العربية أو أي نص غير إنجليزي يجب استخدام `mb_strlen()` دائماً.

```php
strlen("مرحبا")    // 10 ← bytes
mb_strlen("مرحبا") // 5  ← حروف
```

---

**السؤال الرابع:** ما الإعدادات اللازمة لضمان حفظ النصوص العربية والـ Emojis بشكل صحيح في تطبيق Laravel؟

```
MySQL:
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci
على مستوى قاعدة البيانات والجداول والأعمدة

Laravel (config/database.php):
'charset'   => 'utf8mb4',
'collation' => 'utf8mb4_unicode_ci',

PHP:
json_encode($data, JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES)

HTTP Headers:
Content-Type: application/json; charset=UTF-8
```

القاعدة: UTF-8 في كل طبقة من Client إلى HTTP إلى PHP إلى MySQL وعودة.

---

**السؤال الخامس:** لماذا تبدأ ملفات JPEG بـ FF D8 FF دائماً؟

لأنها Magic Bytes أو File Signature، وهي bytes ثابتة في بداية الملف تُعرّف نوعه الحقيقي بغض النظر عن امتداده. تستخدمها أنظمة التشغيل والبرامج للتحقق من نوع الملف الفعلي. في أمان رفع الملفات يجب التحقق من MIME Type المبني على Magic Bytes وليس الاكتفاء بالامتداد الذي يمكن تزويره.

---

**السؤال السادس:** حوّل اللون #1A2B3C إلى قيم RGB.

```
1A = 1×16 + 10 = 26
2B = 2×16 + 11 = 43
3C = 3×16 + 12 = 60

RGB(26, 43, 60)
```

## ملاحظات الأداء والأمان

- استخدام BIGINT للـ IDs من اليوم الأول يمنع مشاكل Overflow المستقبلية.
- عدم استخدام Float للمبالغ المالية يمنع أخطاء الحساب في الأنظمة المالية.
- التحقق من Magic Bytes وليس الامتداد عند رفع الملفات يمنع رفع ملفات خبيثة.
- utf8mb4 في MySQL يدعم كل لغات العالم والـ Emojis ويجب أن يكون الافتراضي في كل مشروع.

## ملخص

الحاسوب يستخدم النظام الثنائي لأسباب فيزيائية تتعلق بطبيعة الترانزستور وليس لأسباب تصميمية اعتباطية. كل بيانات الحاسوب أرقاماً كانت أم نصوصاً أم صوراً تُختزل في النهاية لأصفار وآحاد. فهم كيفية تخزين الأنواع المختلفة يمكّن مهندس الـ Backend من تجنب أخطاء شائعة وخطيرة كاستخدام Float للمال واستخدام utf8 بدلاً من utf8mb4 والاعتماد على الامتداد بدلاً من Magic Bytes في التحقق من الملفات.
