## شرح المفاهيم

### أولاً: تعريف الحاسوب

الحاسوب آلة تستقبل بيانات، تعالجها وفق تعليمات محددة، ثم تنتج نتيجة. يقوم هذا التعريف على أربعة عناصر جوهرية: المدخلات، والمعالجة، والمخرجات، والبرنامج الذي يحكم هذه العملية.

```
Input  →  Process  →  Output
(مدخلات)   (معالجة)   (مخرجات)
```

### ثانياً: Hardware و Software

الـ Hardware هو كل مكون مادي يمكن لمسه، كالشاشة ولوحة المفاتيح والقرص الصلب. أما الـ Software فهو التعليمات التي تخبر الـ Hardware ماذا يفعل، كنظام التشغيل والتطبيقات والكود الذي يكتبه المطور.

```
Software
├── التطبيقات
└── نظام التشغيل
─────────────────
Hardware
├── CPU
├── RAM
├── Storage
└── ...
```

### ثالثاً: المعالج — CPU

المعالج هو دماغ الحاسوب. يقوم بثلاث خطوات متكررة بمليارات المرات في الثانية:

```
FETCH    →    DECODE    →    EXECUTE
(الجلب)      (فك الترميز)    (التنفيذ)

يجلب التعليمة   يفهم معناها   ينفذها فعلياً
من الذاكرة
```

سرعة المعالج تُقاس بالـ GHz، حيث يعني 3 GHz ثلاثة مليارات دورة في الثانية. كما يحتوي المعالج الحديث على عدة Cores تتيح معالجة عدة مهام في وقت واحد فعلياً.

### رابعاً: أنواع الذاكرة

```
هرم الذاكرة من الأسرع للأبطأ:

Registers     ← أسرع / بضع bytes / داخل المعالج
L1 Cache      ← 1 ns  / 32-64 KB
L2 Cache      ← 5 ns  / 256 KB - 1 MB
L3 Cache      ← 20 ns / عدة MB
RAM           ← 100 ns / 8-64 GB
SSD           ← 100 µs / مئات GB
HDD           ← 10 ms  / عدة TB
```

**RAM:** ذاكرة سريعة مؤقتة تحتوي البرامج قيد التشغيل. تُمسح فور انقطاع الكهرباء لأنها تخزن البيانات كشحنات كهربائية في Capacitors تحتاج طاقة مستمرة. هذا تصميم مقصود يحقق السرعة العالية.

**Storage:** ذاكرة دائمة أبطأ نسبياً. تبقى البيانات فيها حتى بعد إغلاق الجهاز.

**Cache:** ذاكرة صغيرة جداً داخل المعالج نفسه. يحتفظ فيها المعالج بالبيانات الأكثر استخداماً للوصول الفوري دون الرجوع للـ RAM.

**ROM:** ذاكرة القراءة فقط. صغيرة وثابتة تحتوي برامج لا تتغير كالـ BIOS الذي يعمل فور تشغيل الجهاز قبل أي نظام تشغيل.

### خامساً: من الكود إلى التنفيذ

المعالج لا يفهم PHP أو Python أو أي لغة برمجة. يفهم فقط Machine Code — أصفاراً وآحاداً. توجد ثلاث طرق لسد هذه الفجوة:

**Compilation:** يترجم الكود كاملاً مرة واحدة قبل التشغيل وينتج ملفاً تنفيذياً. سريع جداً في التنفيذ لكن مرتبط بنظام تشغيل محدد. أمثلة: C, Go, Rust.

**Interpretation:** يفسر الكود سطراً بسطر أثناء التشغيل. مرن لكن أبطأ. أمثلة: Python, Ruby.

**JIT Compilation:** يراقب الكود أثناء التشغيل ويترجم الأجزاء الأكثر استخداماً إلى Machine Code. يجمع مزايا الطريقتين. أمثلة: PHP 8, Java.

PHP يمر بمراحل: Source Code → Tokens → AST → Opcodes → Zend Engine → CPU.

## الأسئلة والإجابات

**السؤال الأول:** ما الفرق بين RAM و Storage؟

الـ RAM ذاكرة سريعة مؤقتة تحتوي البرامج قيد التشغيل وتُمسح بانقطاع الكهرباء. أما الـ Storage فذاكرة دائمة أبطأ تحتفظ بالبيانات والملفات بصفة دائمة.

---

**السؤال الثاني:** لماذا تُمسح الـ RAM عند إغلاق الجهاز وليس هذا عيباً؟

لأن الـ RAM تخزن البيانات كشحنات كهربائية في Capacitors تحتاج طاقة مستمرة للبقاء. عند انقطاع الكهرباء تتبدد الشحنات وتختفي البيانات. هذا تصميم مقصود لتحقيق سرعة عالية جداً، إذ إن الـ Capacitor الذي يفقد شحنته بسرعة هو نفسه الذي يُشحن ويُفرغ بسرعة هائلة. السرعة والدوام في تعارض، واختار المهندسون السرعة للـ RAM والدوام للـ Storage.

---

**السؤال الثالث:** ما الفرق بين Compiled و Interpreted Languages؟

الـ Compiled Languages تترجم الكود كاملاً مرة واحدة إلى Machine Code قبل التشغيل فتنتج ملفاً تنفيذياً سريعاً لكنه مرتبط بنظام تشغيل محدد. أما الـ Interpreted Languages فتفسر الكود سطراً بسطر أثناء التشغيل مما يمنحها مرونة أعلى على حساب السرعة.

---

**السؤال الرابع:** لماذا PHP 8 أسرع من PHP 7؟

لأن PHP 8 أضافت JIT Compilation التي تترجم أجزاء الكود الأكثر استخداماً إلى Machine Code أثناء التشغيل بدلاً من الاقتصار على تفسير الـ Opcodes بواسطة Zend Engine في كل مرة.

---

**السؤال الخامس:** إذا كان الجهاز يحتوي 8 GB RAM وفُتح 20 برنامجاً في وقت واحد، ماذا يحدث؟

تمتلئ الـ RAM فيلجأ نظام التشغيل إلى استخدام Virtual Memory بنقل الصفحات الأقل استخداماً إلى Swap Space على الـ Storage. بما أن الـ Storage أبطأ بكثير من الـ RAM يحدث تباطؤ ملحوظ. إذا امتلأ Swap Space أيضاً قد يتدخل OOM Killer لإغلاق بعض البرامج قسراً.

---

**السؤال السادس:** ما الفرق بين 32-bit و 64-bit في سياق الـ CPU والـ RAM؟

المعالج 32-bit يستطيع عنونة 2³² موقع في الذاكرة أي ما يعادل 4 GB كحد أقصى للـ RAM. المعالج 64-bit يستطيع عنونة 2⁶⁴ موقع مما يجعل سقف الـ RAM نظرياً لا حدود له عملياً. تطبيقات الـ Backend الحديثة قد تحتاج عشرات الـ GB للـ Caching، وهذا ما جعل المعالجات 32-bit غير كافية.

---

**السؤال السابع:** لماذا يختلف Backend Engineer عن Frontend Engineer في احتياجه لفهم الـ Hardware؟

لأن الـ Backend Engineer يتعامل مباشرة مع السيرفرات وأدائها. عندما يكون التطبيق بطيئاً يحتاج تشخيص ما إذا كانت المشكلة في CPU أو RAM أو Disk I/O. وعند اختيار سيرفر يحتاج تحديد RAM و CPU Cores المناسبين. وعند نشر التطبيق بـ Docker يحتاج تحديد Resource Limits لكل Container. هذه قرارات تستلزم فهم الـ Hardware وليس مجرد كتابة الكود.

## ملاحظات الأداء

- الاختناق في تطبيقات Web غالباً في Database و Network I/O وليس في قوة المعالج.
- تفعيل OPcache يقلل وقت تحميل Laravel من ~100ms إلى ~15ms.
- استخدام BIGINT بدلاً من INT للـ IDs في MySQL يمنع Overflow عند تجاوز 2.1 مليار سجل.
- عدم استخدام Float لتخزين المبالغ المالية تفادياً لـ Floating Point Precision Error.

---

## ملخص

الحاسوب آلة لمعالجة البيانات تعتمد على تعاون وثيق بين الـ Hardware والـ Software. المعالج ينفذ دورة Fetch-Decode-Execute بمليارات المرات في الثانية، والذاكرة منظمة في هرم يوازن بين السرعة والسعة والدوام. الكود الذي يكتبه المطور يمر بسلسلة تحويلات قبل أن يصل إلى المعالج بصورة يفهمها. فهم هذه الطبقات يمكّن مهندس الـ Backend من تشخيص مشاكل الأداء واتخاذ قرارات هندسية صحيحة.
