## شرح المفاهيم

### أولاً: نشأة Linux

عام 1969 كتب مهندسو Bell Labs نظام Unix — مستقر وقوي ومصمم للسيرفرات. لكنه كان مملوكاً لشركة AT&T ولا يمكن استخدامه بحرية. عام 1991 كتب Linus Torvalds وهو طالب فنلندي عمره 21 عاماً نواة نظام تشغيل مفتوحة المصدر أسماها Linux. اليوم:

```
96.3% من أكبر 1,000,000 سيرفر في العالم تعمل بـ Linux.
100% من أسرع 500 سوبر كمبيوتر في العالم تعمل بـ Linux.
Android المبني على Linux Kernel على أكثر من 3 مليار جهاز.
AWS و Google Cloud و Azure كلها تعمل بـ Linux.
```

### ثانياً: لماذا Linux وليس Windows للسيرفرات؟

| المعيار | Linux | Windows |
|---------|-------|---------|
| التكلفة | مجاني 100% | مئات الدولارات لكل سيرفر |
| الاستقرار | يعمل لسنوات بدون Restart | يحتاج Restart دورياً |
| الأمان | أقل استهدافاً | هدف رئيسي للـ Malware |
| الأداء | أخف على الموارد | أثقل |
| التحكم | كامل 100% | محدود |
| المصدر | مفتوح — يمكن تعديل الـ Kernel | مغلق |

```
تكلفة Downtime في شركة كبرى:

Restart واحد = 5 دقائق Downtime
52 Restart في السنة = 260 دقيقة
في شركة مثل Amazon = خسارة تتجاوز $200,000

Linux Servers تعمل لسنوات بدون Restart.
```

السبب الأعمق لاستخدام Supercomputers لـ Linux: كونه مفتوح المصدر يُتيح للعلماء والمهندسين تعديل الـ Kernel نفسه وتحسينه لمهامهم المحددة. Windows المغلق لا يسمح بهذا.

### ثالثاً: Linux Kernel مقابل Linux Distribution

```
Linux Kernel:
النواة الأساسية فقط.
تتحدث مع الـ Hardware.
لا يمكن استخدامها وحدها كنظام تشغيل كامل.

Linux Distribution:
Linux Kernel
+ Package Manager
+ أدوات النظام
+ برامج إضافية
+ واجهة المستخدم
= نظام تشغيل كامل قابل للاستخدام
```

### رابعاً: أشهر Distributions للـ Backend

**Ubuntu:** الأكثر شيوعاً للمبتدئين والـ Production. Package Manager: apt. تحديثات منتظمة مع إصدارات LTS. مجتمع ضخم ودعم واسع من Cloud Providers. الخيار الموصى به لتطبيقات Laravel.

**Debian:** الأكثر استقراراً. Ubuntu مبنية عليها. تحديثات أبطأ مما يعني استقراراً أعلى. Package Manager: apt.

**CentOS / RHEL:** الأكثر استخداماً في المؤسسات الكبيرة. Package Manager: yum أو dnf.

**Alpine:** مصممة لتكون خفيفة جداً. حجمها 5 MB فقط مقارنة بـ 2+ GB لـ Ubuntu. مثالية للـ Docker Images. تستخدم musl libc بدلاً من glibc مما يُسبب أحياناً مشاكل توافقية مع بعض المكتبات المبنية لـ glibc.

### خامساً: الـ Shell

الـ Shell البرنامج الذي يستقبل أوامرك النصية ويحولها إلى System Calls ينفذها الـ Kernel.

```
أنت تكتب: ls -la
               │
               ▼
            Shell
               │
      يحول الأمر لـ System Calls
               │
               ▼
            Kernel
               │
               ▼
        يُعيد النتيجة
               │
               ▼
            Shell
               │
        يعرضها لك
```

**bash:** الافتراضي في معظم Linux Servers. الأكثر شيوعاً في بيئة الـ Production. ستتعامل معه في 95% من السيرفرات.

**zsh:** أحدث وأقوى. يدعم Plugins و Themes. الافتراضي في macOS الحديثة. مناسب للـ Development Environment المحلية.

**sh:** Shell الأصلي البسيط. يُستخدم في Scripts لضمان التوافقية مع كل البيئات.

### سادساً: Terminal مقابل Shell مقابل CLI

```
Terminal:
البرنامج الذي يعرض نافذة النص.
مثل: GNOME Terminal, iTerm2, Windows Terminal.
هو مجرد نافذة.

Shell:
البرنامج الذي يعمل داخل الـ Terminal.
يفهم أوامرك وينفذها.
مثل: bash, zsh.

CLI:
طريقة التفاعل بالنص بشكل عام.
عكسها: GUI.
```

### سابعاً: لماذا CLI وليس GUI في السيرفر؟

```
السبب الأول — الموارد:
GUI تستهلك CPU وRAM لرسم النوافذ.
السيرفر يجب أن يوجه كل موارده للتطبيق.

السبب الثاني — Remote Access:
السيرفر في معظم الأحيان لا شاشة متصلة به.
التحكم يتم عن بُعد عبر SSH.
CLI عبر SSH سريع وخفيف.
GUI عبر الشبكة بطيء جداً.

السبب الثالث — الأتمتة:
أوامر CLI تُوضع في Scripts وتعمل تلقائياً.
GUI لا يمكن أتمتته بسهولة.

السبب الرابع — القوة:
أوامر CLI تُنجز في ثوانٍ ما يأخذ دقائق في GUI.
```

### ثامناً: خيارات البداية مع Linux

```
WSL2:
تشغيل Linux Kernel حقيقي داخل Windows
عبر Hyper-V VM خفيفة مدمجة.
يتشارك الملفات مع Windows بسهولة.
مناسب للتعلم والتطوير.
بعض الـ System Calls قد تتصرف
بشكل مختلف عن Linux الحقيقي.

Virtual Machine:
Linux كامل معزول تماماً.
أثقل على الموارد.
أقرب لبيئة الـ Production.
مناسب لاختبار الـ Deployment.

Cloud VPS:
سيرفر Ubuntu حقيقي.
الأقرب للـ Production الفعلي.
$5 شهرياً على DigitalOcean أو AWS.
الخيار الأفضل بعد إتقان الأساسيات.

Docker:
docker run -it ubuntu bash
الأسرع للتجربة السريعة.
```

## الأسئلة والإجابات

**السؤال الأول:** لماذا يختار المهندسون CLI على GUI في بيئة السيرفر؟

لأن CLI يستهلك موارد أقل ويوجه طاقة السيرفر للتطبيق بدلاً من رسم النوافذ. السيرفرات في الغالب لا شاشة متصلة بها والتحكم فيها عن بُعد عبر SSH حيث CLI خفيف وسريع بينما GUI بطيء عبر الشبكة. إضافة إلى ذلك يمكن أتمتة أوامر CLI في Scripts لتعمل تلقائياً بينما أتمتة GUI معقدة وغير عملية.

---

**السؤال الثاني:** ما الفرق بين Linux Kernel و Linux Distribution؟ أعطِ مثالين.

Linux Kernel النواة الأساسية التي تتحدث مع الـ Hardware مباشرة ولا يمكن استخدامها وحدها كنظام تشغيل. Linux Distribution هو الـ Kernel مضافاً إليه Package Manager وأدوات النظام وبرامج إضافية لتكوين نظام تشغيل كامل قابل للاستخدام. مثالان: Ubuntu تستخدم apt وتستهدف سهولة الاستخدام. Alpine تستخدم apk وتستهدف الحجم الصغير للـ Docker.

---

**السؤال الثالث:** ما هو الـ Shell وما الفرق بين bash و zsh؟

الـ Shell البرنامج الذي يستقبل الأوامر النصية ويفسرها ويحولها إلى System Calls ينفذها الـ Kernel. bash الافتراضي في معظم Linux Servers وهو الأكثر شيوعاً في Production. zsh أحدث ويدعم Plugins و Themes وهو الافتراضي في macOS الحديثة ومناسب للـ Development المحلي.

---

**السؤال الرابع:** أي Distribution تختار لـ Production Server يعمل بـ Laravel ولماذا؟

Ubuntu لأنها سهلة التعلم ولها مجتمع ضخم يعني توفر حلول لكل مشكلة. تحديثاتها منتظمة مع إصدارات LTS توفر استقراراً طويل المدى. تدعمها كل Cloud Providers الكبرى افتراضياً مما يُسهل الـ Deployment والتكامل مع الخدمات السحابية.

---

**السؤال الخامس:** لماذا Alpine مثالية للـ Docker وليست مثالية كـ Development Environment؟

لأنها مصممة لتكون خفيفة جداً بحجم 5 MB فقط مما يُقلل حجم Docker Images ويُسرع نقلها وتشغيلها. لكن قلة الأدوات والمكونات المثبتة افتراضياً تجعلها أقل راحة كبيئة تطوير كاملة. إضافة إلى أنها تستخدم musl libc بدلاً من glibc مما يُسبب أحياناً مشاكل توافقية مع مكتبات مبنية لـ glibc.

---

**السؤال السادس:** WSL2 أم Virtual Machine لمطور على Windows يريد تعلم Linux؟

WSL2 للتعلم والتطوير اليومي لأنه أسهل في الإعداد ويتشارك الملفات مع Windows بسهولة وأداؤه ممتاز. Virtual Machine عندما يحتاج Linux كامل معزول تماماً أو لاختبار Deployment قبل الـ Production. بعد إتقان الأساسيات ينتقل المطور لـ Cloud VPS الأقرب للبيئة الحقيقية.

---

**السؤال السابع:** خطة تحويل 100 Windows Server إلى Linux.

```
1. Assessment:
   توثيق كل سيرفر وتطبيقاته ومتطلباته.

2. اختيار Distribution:
   Ubuntu في الغالب للـ Web Servers.

3. Pilot Migration:
   تحويل 2-3 سيرفرات غير حرجة أولاً.

4. اختبار شامل:
   Applications, Databases, Networking,
   Performance, Security.

5. Migration تدريجية:
   تحويل مجموعات صغيرة مع مراقبة.

6. Rollback Plan:
   خطة واضحة للعودة عند أي مشكلة.

7. Documentation:
   توثيق كل خطوة وكل مشكلة وكل حل.
```

المخاطر: Application Compatibility، نقص خبرة الفريق، Downtime أثناء التحويل، تكاليف التدريب والاستشارات قد تتجاوز الوفر في السنة الأولى.

## ملاحظات مهمة

- في Production ستتعامل مع bash في 95% من الحالات. إتقانه أولوية قبل zsh.
- Ubuntu LTS الخيار الأضمن للمشاريع التجارية بسبب دعمها الطويل الأمد.
- Alpine مناسبة للـ Docker Images لكن يجب اختبار توافقية المكتبات قبل اعتمادها.
- التحول من Windows لـ Linux قرار استراتيجي يحتاج تخطيطاً دقيقاً وتوثيقاً كاملاً.

## ملخص

Linux هو الخيار السائد للسيرفرات لأسباب هندسية واقتصادية: مجاني ومستقر ومفتوح المصدر يُتيح تخصيصه الكامل. الـ Kernel النواة الأساسية والـ Distribution النظام الكامل الجاهز للاستخدام. الـ Shell وسيط بين المستخدم والـ Kernel والـ Terminal مجرد نافذة عرض. CLI ليس مجرد أسلوب قديم بل هو الأداة الأنسب لبيئة السيرفر من حيث الموارد والأتمتة والتحكم عن بُعد. مهندس الـ Backend يتعامل مع Linux يومياً في الـ Deployment والـ Debugging وإدارة السيرفرات لذلك إتقانه ضرورة وليس خياراً.
